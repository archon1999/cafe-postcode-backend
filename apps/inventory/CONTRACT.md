# Inventory contract

Base: `/api/v1/admin/inventory/`. Existing admin authentication and selected-restaurant scope apply. JSON keys are camelCase; UUID strings identify records; decimal quantities/costs/values are strings. Dates are ISO. Lists return arrays (documents and movements support `limit`, default 200/max 1000, and `offset`). All validation failures use existing DRF 400 responses. Archived reference records remain in history.

## References
- `GET/POST warehouses/`; `GET/PATCH warehouses/{id}/`: `{id,name,kind,isActive,isDefault,createdAt,updatedAt}`. `kind`: `general|raw|production|sales`. POST/PATCH name/kind/isActive/isDefault. One default warehouse is created lazily on first GET. POS uses default.
- `GET/POST items/`; `GET/PATCH items/{id}/`: `{id,name,sku,kind,baseUnit,purchaseUnit,purchaseFactor,minQuantity,tolerancePercent,toleranceQuantity,toleranceValue,availabilityMode,isActive,createdAt,updatedAt}`. `kind`: `raw|semi_finished|finished|packaging|non_food`; baseUnit: `g|ml|piece`; purchaseUnit is label (kg, l, lotok), purchaseFactor base units per purchase unit, positive decimal. Defaults factor=1, minQuantity=0, tolerances percent=5/quantity=0/value=0, availabilityMode=`warn`; modes `off|warn|block`. Unit cannot change after movement or recipe use. `search` query supported.
- `GET/POST suppliers/`; `GET/PATCH suppliers/{id}/`: `{id,name,taxNumber,phone,address,isActive,createdAt,updatedAt}`.

## Recipes
- `GET recipes/` returns all current recipe versions; `catalogItem={uuid}` and `outputItem={uuid}` filters are supported; `GET recipes/{id}/` reads an immutable version.
- `POST recipes/` creates a new active version and deactivates the old version for the same target. Exactly one target is required: `catalogItem` for a POS product or `outputItem` for a preparation. Catalog form: `{catalogItem,name?,yieldQuantity:"1",trigger:"dispatch",lines:[{item,quantity:"100",modifierOption:null,modifierCondition:"selected"}]}`. With a modifier, `selected` adds the ingredient only when that option is chosen; `not_selected` keeps a base ingredient unless an “without …” option is chosen. Preparation form: `{outputItem,name?,yieldQuantity:"100",lines:[{item,quantity:"120"}]}`. Preparation output must be a `semi_finished` or `finished` item, cannot use modifiers and cannot form a recipe cycle. Trigger `dispatch|sale` applies to catalog recipes. Output additionally identifies `targetType:"catalog"|"preparation"`, target names, estimated cost and immutable version.
- `PATCH recipes/{id}/` accepts only `{isActive:false}` (reactivation uses POST new version).

## Documents
- `GET documents/` supports `kind,status,warehouse,search,limit,offset`; `GET documents/{id}/`.
- `POST documents/`: `{kind,warehouse,destinationWarehouse:null,productionRecipe:null,plannedQuantity:null,actualQuantity:null,supplier:null,reference:"",reason:"",occurredAt?:ISO,attachmentUrl:"",responsibleName:"",notes:"",idempotencyKey?:uuid,lines:[{item,quantity,unitCost:"0",listUnitCost:"0",discountPercent:"0",discountAmount:"0",inputUnit:"base",lotNumber:"",expiresOn:null}]}`. Kinds `opening|receipt|issue|supplier_return|customer_return|stocktake|transfer|production`; all create draft. Transfer requires a distinct destination warehouse and explicitly supplied product lines. Production requires an active preparation recipe and planned/actual output; input/output lines are derived by the server. `inputUnit` is `base|purchase`; quantity converts to base with the item factor. For inbound rows `unitCost` input is the supplier list price; the server snapshots it as `listUnitCost` and stores the discounted net value as `unitCost`. Percentage and fixed discounts cannot exceed the list value. Issues and transfer source use weighted average. Stocktake quantity is actual counted base quantity (zero allowed), all other quantities positive. Reasons are mandatory for issue/returns/stocktake on posting. Supplier is mandatory for receipt/supplier_return. Reference/responsibleName are required on posting for all manual documents.
- Start a stocktake with each `quantity:null`; this captures balance/revision before counting. Output `quantity:null,countRecorded:false` until actual quantity is entered by PATCH. Zero is a real completed count. Posting rejects every uncounted line.
- `PATCH documents/{id}/` edits draft; supplied lines replace draft lines. Warehouse/kind cannot change. Stocktake expected quantity, cost and ledger revision are captured at creation; movement on any counted item before post rejects posting (409 semantics via 400 message), requiring a new stocktake. This prevents applying stale counts while POS continues.
- `POST documents/{id}/post/` empty body: post transactionally, repeated request returns same posted document. Creates immutable ledger; negative stock allowed for POS/warn, manual issues cannot exceed stock unless `{allowNegative:true}` supplied on post (permission same posting). Completed documents cannot be edited/deleted.
- `POST documents/{id}/reverse/` body `{reason}`: create posted reversal linked via `reversalOf`; original status becomes `reversed`; retries return existing reversal. Stocktake reversal permitted only if counted-item revisions still match the posted stocktake; movements require a fresh corrective count. Source document remains intact.
- `GET documents/{id}/export/` CSV with document metadata and lines, safe against spreadsheet formula injection.
- Document output adds `destinationWarehouse`, `destinationWarehouseName`, `productionRecipe`, `productionRecipeName`, `plannedQuantity`, `actualQuantity`; line output adds `role:normal|input|output`, `listUnitCost`, `discountPercent`, and `discountAmount`. `status`: draft|posted|reversed. Service kinds `sale|sale_return|reversal` are read only.

## Reports and recommendations
- `GET balances/?warehouse={uuid}`: array `{item,itemName,itemKind,sku,baseUnit,warehouse,warehouseName,quantity,averageCost,value,minQuantity,availabilityMode,isLow,isNegative,lastCountedAt,updatedAt}` including zero-stock active items.
- `GET movements/?warehouse=&item=&kind=&from=YYYY-MM-DD&to=YYYY-MM-DD&limit=&offset=`: array `{id,document,documentNumber,kind,item,itemName,baseUnit,warehouse,quantity,unitCost,value,balanceAfter,occurredAt,createdAt,orderItem}` (quantity/value signed).
- `GET overview/?warehouse=&from=&to=`: `{stockValue,itemCount,lowStockCount,negativeStockCount,receiptValue,issueValue,saleCost,varianceValue,varianceQuantityCount,lastCountedAt}`. Value metrics period filtered; current balances as of now.
- `GET variance/?warehouse=&from=&to=`: array `{document,documentNumber,occurredAt,item,itemName,baseUnit,expectedQuantity,actualQuantity,varianceQuantity,varianceValue,consumptionQuantity,variancePercent,tolerancePercent,toleranceQuantity,toleranceValue,requiresAttention}`. Denominator is recipe consumption since previous posted count/opening; absent consumption => null percent (never invented).
- `GET insights/?warehouse=`: `{mode:"rules",aiAvailable:boolean,generatedAt,items:[{id,severity:"info|warning|critical",title,detail,item:null,evidence:{...},recommendation}]}`. Explainable shortages/low stock, estimated days remaining, variances and expiring receipt lots (expiry evidence does not claim exact remaining lot quantity). Distinct AI analysis endpoint may be added by root.
- `GET export/?report=balances|movements|variance&warehouse=&from=&to=` downloads CSV.

Permissions: `admin.inventory.view` required for every endpoint; `admin.inventory.manage` POST/PATCH references+recipes+documents; `admin.inventory.post` document post/reverse. `admin.inventory.view_cost` controls all monetary fields (null without permission) and cost inputs. Price-only insights omitted without cost permission. CSV omits monetary columns. AI analysis additionally requires `admin.inventory.analyze`.

Additional references: `GET catalog-options/` returns `[{id,name,saleUnit,modifierOptions:[{id,name,groupName}]}]` using inventory permission. `POST attachments/` multipart `file` PDF/PNG/JPEG max10MB returns `{id,name,url}`; `GET attachments/{id}/download/` is authenticated and restaurant scoped, use admin API client to download. attachmentUrl accepts the absolute returned URL unchanged.

Document additive fields: `purchaseValue` is inbound baseQuantity × baseUnitCost sum; `valuationAdjustment` is explicit carrying-value reconciliation for provisional negative stock. Ledger value includes this adjustment and always matches balance value; purchase value remains the original invoice amount. `consumptions` stores `[{orderItem,recipe,recipeVersion,quantity,resolvedQuantity,resolutions:[{disposition,quantity,createdAt,createdByName}]}]` so waste/allocation/physical returns remain visible without duplicate stock outflow.

## POS service hooks (Python)
`consume_order_items(order, items, actor=None)` at confirmed dispatch, transactionally creates idempotent sale document per item and persists recipe ingredients/costs snapshot. No recipe means no movement. Repeated dispatch does not consume twice. Optional `event_key` supports quantity split callers; default stable order-item id.
`cancel_order_item(item, disposition="waste", actor=None, quantity=None, event_key=None)` where `restore` returns original consumption proportion at original costs; `waste` records cancellation but never adds or double-subtracts stock. Whole-item repeats idempotent. `quantity` in sold units, bounded by original consumed minus already resolved. Caller must provide stable event_key for partial repeatable cancellations/returns.
`get_menu_inventory(catalog_item, modifier_options=None)` -> `{tracked,blocked,lowStock,availableQuantity,reason,updatedAt}` (snake_case internally); checks base recipe and selected modifiers. `block` ingredients require minimum sold unit (1 piece, 0.001 kg). Never changes manual stop-list.
`has_consumption(item)` identifies quantities requiring a durable split.
`inventory_snapshot(restaurant)` -> JSON-safe `{version:1,updatedAt,warehouseId,warehouses,items,balances,recipes,consumptions}` for local-agent deterministic parity; UUIDs/decimals strings and snake_case internal keys (HTTP camelcases). Warehouses `{id,name,isDefault}`, items `{id,name,baseUnit,availabilityMode,minQuantity}`, balances `{warehouseId,itemId,quantity,revision}`, recipes `{id,catalogItemId,version,yieldQuantity,trigger,saleUnit,lines:[{itemId,quantity,modifierOptionId,modifierCondition}]}`, active-order consumptions `{orderItemId,recipeId,recipeVersion,quantity,resolvedQuantity,warehouseId,components:[{itemId,quantity}]}`. No costs in bootstrap.
`inventory_replay_context(restaurant,snapshots,occurred_at)` accepts trusted edge snapshots map keyed order item UUID (or list), each `{orderItemId,recipeId,recipeVersion,quantity,warehouseId,components:[{itemId,quantity}]}`. It validates persisted immutable recipe and ingredient totals, preserves historical warehouse, and permits historic consumption despite now-short stock. Late events posted after a completed count get explicit reconciliation warning; another physical count clears that warning. Ordinary HTTP cannot enter this context.
